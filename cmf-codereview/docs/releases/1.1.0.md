# cmf-codereview 1.1.0

Version 1.1.0 adds deployment Process Rule validation and SARIF reporting. The checks help reviewers identify unsafe deployment patterns before installation, and SARIF makes findings available to compatible static analysis tools.

**Release preparation:** the package passed automated validation. Publication and integration testing in a consuming project's PR pipeline are manual; these notes do not confirm that the package has been published to a registry.

## Process Rule validation

Deployment-specific checks run automatically when Process Rules are included in a DEEs/Both scan. They use C# syntax and package metadata; no guideline file, AI service, or additional validation flag is required.

- **Deployment guards and safe reruns:** flag logic placed in `DeeTestCondition`, which deployment skips, and supported mutations without matching existence/state guards in `DeeActionCode`.
- **Attribute changes:** check supported property-update patterns for existence guards, cleanup before removal, and subsequent schema regeneration for the same entity type.
- **Transaction hazards:** flag recognized Smart/Generic Table data operations when their schema is created or structurally changed by the same package version. Moving an operation to an After folder alone does not avoid this deployment transaction risk.
- **Placement and ordering:** check supported folder/content/namespace conventions, namespace-to-folder version consistency, and resolvable entity-type creator/consumer ordering.
- **Recurring migrations:** identify migration-like operations under unversioned Services that will run on every deployment.

Unresolved helper behavior or dependencies can produce review findings rather than a claim that deployment is safe. The [rule reference](../rules.md#process-rule-deployment-validation) lists diagnostic IDs, severities, supported patterns, and limitations.

Delivery: User Story #52869, [PR #3](https://github.com/criticalmanufacturing/cli-plugins/pull/3).

## SARIF 2.1.0 reporting

`scan`, `report`, and `review` can emit SARIF 2.1.0. Results include the rule ID, description, suggested fix, source path, and line number when known. Critical/High findings map to SARIF `error`; Medium maps to `warning`.

```bash
# Scan directly to SARIF.
cmf-codereview scan --repository-root . --report-format Sarif --output findings.sarif

# Convert an existing findings JSON file to SARIF.
cmf-codereview report --findings-path findings.json --report-format Sarif --report-path report.sarif
```

JSON remains the default scan output. Existing filtering, suppressions, baselines, and exit-code policy apply before SARIF rendering. Standard and Detailed report modes produce the same SARIF log. The `report --findings-path` input remains the original findings JSON, not a SARIF log.

Posting annotations or comments requires a separately configured pipeline consumer. This release does not generate or scaffold pipelines. See the [command reference](../commands.md#sarif-output).

Delivery: User Story #50197, [PR #4](https://github.com/criticalmanufacturing/cli-plugins/pull/4).

## Upgrade and usage notes

New Process Rule diagnostics can introduce additional High or Critical findings. An existing `scan --fail-on High` or `--fail-on Critical` gate can therefore start failing after the upgrade, even if the pipeline command is unchanged.

Review the findings before enabling the new package across the team. Use the existing per-rule configuration, targeted suppressions, or a reviewed baseline for accepted debt. Create corrections in a new deployment version rather than editing already-shipped Process Rules solely to clear historical findings.

```bash
# Run from the customization repository after restoring its dependencies.
dotnet restore
cmf-codereview scan --repository-root . --output findings.json
cmf-codereview report --findings-path findings.json --report-format Html --report-path report.html
```

Use `--roots` when a non-standard repository layout cannot be discovered from package metadata. Restored project dependencies remain necessary for the existing entity-aware rules. See [configuration](../configuration.md) and [commands](../commands.md).

## Known limitations and excluded scope

- Static checks cover recognized syntax and metadata patterns. They do not execute a deployment, prove arbitrary external helpers or callbacks safe, or verify database reruns and data preservation. Test both initial installation and repeated execution against the target environment.
- **Known schema-check gap:** `IEntityType.AddProperties(...)` is not covered by `ProcessRuleSchemaRegeneration` in this version. A clean scan does not validate schema regeneration for that operation. The implemented schema checks cover supported property-collection `Create()` and `FullUpdateEntityType(...)` patterns.
- Action Group intelligence and runtime trace correlation are deferred to v1.2.0 and are not included here.
- Pipeline generation/re-scaffolding and the remaining performance backlog are not delivered by this release; no scan-speed improvement is claimed.
- DEE UseReference and deployment-folder/package-version validation from [PR #5](https://github.com/criticalmanufacturing/cli-plugins/pull/5) is not included. Folder/namespace consistency checks described above are a separate supported Process Rule check.
